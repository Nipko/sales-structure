# Revisiones editables separadas — persistencia y edición E3

El almacén nuevo guarda revisiones de configuración en tablas propias, con un puntero al borrador actual. No modifica `agent_personas`, sus canales, su versión operativa ni el alcance de una aprobación pendiente. Cada revisión conserva el hash de la configuración completa y la versión/hash operativos desde los que se preparó.

La escritura exige administrador, tenant propietario del esquema, versión operativa esperada, UUID del borrador esperado y clave de idempotencia. Dos editores concurrentes no sobrescriben el mismo borrador. Repetir una solicitud devuelve su revisión original; reutilizar su clave con otro contenido falla. El historial, el puntero y el comprobante de la solicitud comparten transacción. La lectura comprueba integridad y no crea tablas para ocultar un fallo.

El editor clásico y en modo prompt, el onboarding de un agente existente y las propuestas de Assist ya guardan mediante este contrato. El contexto editable de Assist toma el borrador actual y sólo incluye los campos que sus comandos pueden modificar. Su evaluación de salud sigue siendo de la versión operativa y se identifica así. Los cambios de capacidades conservan los límites del perfil de negocio, los permisos del plan y los requisitos canónicos de agenda; no habilitan herramientas en producción al guardar.

Las rutas administrativas son `GET /persona/:tenantId/agents/:agentId/configuration`, `PUT .../configuration/draft` y `POST .../configuration/draft/discard`. La lectura distingue ausencia, error y borrador con base vencida. El guardado exige la versión operativa, UUID del borrador anterior —o null para el primero—, clave de solicitud y cuerpo completo. Devuelve tanto la revisión guardada como la relectura del espacio actual: repetir una solicitud antigua nunca mueve el puntero de una revisión más nueva. Las mutaciones requieren administrador; la lectura también admite supervisor. El actor procede de la sesión autenticada.

El descarte exige el UUID exacto y la versión/hash operativos recién leídos, registra un comprobante idempotente y elimina sólo el puntero. Conserva el historial inmutable. Permite recuperar un borrador cuya base operativa cambió sin sobrescribir ni certificar sus cambios. Un fallo de auditoría conserva el puntero. Los antiguos PUT de configuración y el setup-wizard que editaba un agente existente devuelven `agent_draft_contract_required`; no existe una ruta alternativa de publicación por guardar. La desactivación conserva su operación inmediata con CAS y aumento de versión; invalida la base del borrador.

Los horarios de cuenta son una revisión separada y explícita de Assist: cambian la configuración global y las versiones de los agentes, sin reescribir sus cuerpos operativos. No se mezclan con un guardado de persona o herramientas. Los cambios de conexiones y agente predeterminado permanecen dentro del borrador.

El editor y el onboarding muestran versión operativa, estado del borrador, base vencida y acciones de prueba/descarte. El laboratorio envía únicamente el UUID actual que devuelve el servidor; reinicia la sesión al cambiar revisión o canal y descarta respuestas tardías. Un vínculo a una revisión antigua falla de forma visible. El onboarding exige guardar sus cambios antes de probar. Los textos nuevos están en español, inglés, portugués y francés.

Este lote no publica ni reactiva agentes y no cambia el enrutamiento operativo. La creación inicial/duplicación, la publicación revisada, el piloto y el rollback pertenecen al siguiente contrato de lifecycle. La creación inicial legacy sigue siendo una frontera explícita pendiente de esa integración; las ediciones de un agente existente están protegidas. Guardar como plantilla continúa tomando la configuración operativa, por lo que la UI lo identifica y bloquea ese flujo si existe borrador. No se desplegaron cambios ni se modificaron tenants de producción.

La validación usó PrismaClient, transacciones de PrismaService y el DDL del proyecto en PostgreSQL temporal de loopback. El cierre pasó 132 pruebas de API en ocho suites, incluidas 33 pruebas PostgreSQL/Prisma: once del almacén original y veintidós del endpoint/Assist. Cubren concurrencia, UUID/hash/versiones, reintentos, cambios de plan, ámbito/rol, rechazo de configuración inválida, descarte e historial, rollback de auditoría, horarios separados y ausencia de escrituras/eventos operativos al guardar. Los esquemas sintéticos de prueba se eliminaron al terminar.

También pasaron TypeScript de API y dashboard, el build compartido, las 460 pruebas globales del dashboard y la repetición final de 22 pruebas de los tres componentes/contratos afectados. La evidencia de UI es renderizado de React y contratos de interacción/selección; no se presenta como navegación autenticada visual. Comandos: `jest --config jest.config.js --runInBand --testPathPattern='agent-draft.postgres|agent-configuration-revision.postgres|copilot.service.context|agent-configuration.service|persona.service.spec|persona-versioned-update|persona-payment-entitlement|setup-wizard-non-destructive'`, `jest --config jest.config.cjs --runInBand`, y `tsc --noEmit --pretty false` en cada aplicación. PostgreSQL se habilitó con `AGENT_REVISION_TEST_DATABASE_URL` sólo para el servicio temporal de loopback.

# REVIEW — Engineering feasibility against the real code (HEAD 0113f68d)

## Verdict
The design is buildable on top of what exists, but §9 systematically undersizes the four pieces that decide whether the promise ("agent replies in step 3, writes in step 5, change anything by touching it") survives contact with the code: (a) the draft/publication layer from d50d1670 makes "write straight to the live agent" and "on/off that really switches on" impossible today (agent-draft.service refuses isActive changes; updateAgent only accepts isActive:false), (b) the recipe has no subtype slot and seeded example prices are real prices in `services`, (c) the public demo page needs a web_widget channel account plus an origin/abuse policy, (d) there is no domain event for "AI actually replied". Biggest risk: building the six screens on the draft pipeline and re-living the 14-sep video with prettier copy.

## Strengths
- Recipe extension is compatible: VerticalDefinition (packages/shared/src/index.ts:1300) is a plain TS interface with LocalizedString fields; every §3.1 addition is an optional field, no new store or migration needed for the static 18-industry part.
- Bootstrap write paths for step 2 already exist and are idempotent per tenant schema: services (verticals.service.ts:2068), faqs (:2121), availability_slots (:2242), companies via business-info.service.ts:160/189; prompt-assembler.service.ts:262-275 already reads company_name/about/phone/website/address/city/country.
- Widget public surface is production-grade: loader.js, config/:widgetId, sessions with WidgetRateLimitService and allowed_domains checks (widget-public.controller.ts:46-140) — the demo page is a thin HTML shell over it, not a new channel.
- The realtime plumbing for step 5 is 80% there: gateway.emitNewMessage fires for the inbound (conversations.service.ts:2259) and for the AI reply (:2357), relayed via Redis so the worker's turns reach the dashboard (agent-console.gateway.ts:603-609).
- POST :tenantId/setup-wizard (persona.controller.ts:198) still has a live-write branch and a `stageOnly` mode, so day-0 stage bookkeeping does not need a new controller.
- onboarding-stage-contract.ts is a single ranked enum with derive-for-legacy semantics; adding a stage is additive and safe.

## Gaps
### E1 [blocking] "Día 0 escribe directo al agente vivo" has no code path: drafts block it at three places
- where: §4 (intro, Paso 3), §5 "Encendido/apagado", §9 row Paso 3
- why: setup-wizard/page.tsx:197-203,335-342 uses saveAgentDraft whenever the tenant has an agent (always on day 0). agent-draft.service.ts:76 throws agent_activation_managed_separately on any isActive change. persona.service.ts:1131-1142 updateAgent only accepts {isActive:false, expectedVersion}. The publication prerequisites (agent-publication-prerequisites.ts) demand samples per channel×language. None of this is mentioned in §9, which sizes Paso 3 as "quitar paneles".
- PROPOSAL: Add a server-side "pre-live commit" rule in agent-draft.service.save(): if deriveOnboardingStage(tenant) < 'live' AND the agent has zero inbound conversations (COUNT(*) FROM conversations WHERE ai_message_count>0 = 0), write the candidate straight into agent_personas inside the same transaction and record a revision with source='onboarding' (so history and agent_config_version stay consistent). Same predicate lets updateAgent accept isActive:true. Post-live, the existing draft→publish flow stays; the editor shows "publicar ahora" only when the predicate is false. Add a postgres spec next to agent-draft.postgres.spec.ts that proves a day-0 save changes serving-persona.ts output immediately.
- evidence: apps/api/src/modules/persona/agent-draft.service.ts:73-76; apps/api/src/modules/persona/persona.service.ts:1131-1142; apps/dashboard/src/app/admin/setup-wizard/page.tsx:335-342

### E2 [blocking] Example prices become real prices the agent quotes (D10 has no data model)
- where: §2 rule "un precio de ejemplo nunca llega a un cliente", §3.1, §4 Paso 2 card 1, D10
- why: The bootstrap inserts VerticalServiceDefinition.price as services.price (verticals.service.ts:2068). Nothing distinguishes seeded from confirmed; the booking/catalog tools and the prompt read services as truth. The "te confirmo el valor" rule exists only in the FAQ text of the generic vertical, not in services.
- PROPOSAL: Expand-contract migration: ALTER TABLE services ADD COLUMN price_status text NOT NULL DEFAULT 'confirmed' ('example'|'confirmed'); bootstrap seeds 'example'; "Usar así"/edit sets 'confirmed'. Prompt/tool layer: services with price_status='example' render without price and with the vertical's confirm-later phrase. Add the column to the tenant_eval_* replica copy list and to setup-fresh/reset-db bootstrap (memory: replicas are partial copies).
- evidence: apps/api/src/modules/verticals/verticals.service.ts:2068; packages/shared/src/index.ts:1257-1266

### E3 [major] Subtypes have no recipe slot; "academia de baile" cannot be a subtype with its own recipe
- where: §3.1, §3.2 first bullet, §3.3, D13
- why: VerticalDefinition.subTypes is Array<{key,label}> only (index.ts:1302). Per-subtype behaviour today lives in a third place, VERTICAL_SUBTYPE_PERSONA_CONTRACTS (persona/vertical-subtype-persona-contract.ts:232), which only carries rules. A dance-academy recipe (Valentina, clase de prueba, Instagram-first) has nowhere to live.
- PROPOSAL: Extend subTypes to `{ key, label, recipe?: Partial<VerticalRecipe> }` where VerticalRecipe is the §3.1 schema (agent, greeting, services, faqs, mainInstructions, unknownFallbacks[3], handoffReasons, recommendedChannels, testQuestions[3], sampleConversations, improvementRecipes, defaultTone, purchaseMechanism). Resolution = industry recipe deep-merged with subtype recipe; getVerticalDefinition(industry, subType) returns the merged object. Fold vertical-subtype-persona-contract rules into recipe.rules so there is one source. Content in 4 languages per LocalizedString as today.
- evidence: packages/shared/src/index.ts:1300-1315; apps/api/src/modules/persona/vertical-subtype-persona-contract.ts:6-21,232

### E4 [major] Public demo page: missing route, missing web_widget channel account, no abuse policy for a shareable link
- where: §4 Paso 4 "Chat web", §7, D11
- why: No public chat page exists (apps/dashboard/src/app has no /w or /demo; landing is static). The widget turn requires a channelAccountId for 'web_widget' (conversations.service.ts:5793; widget-agent-reply.store.ts:71 assertServedAgentConnectionAuthority) — widget.service.createWidget does not create channel_accounts, so day 0 must provision widget + channel account + binding. allowed_domains empty ⇒ allow-all (widget-security.ts:64), but the moment the owner restricts domains for her site, the platform-hosted demo origin is blocked. A shareable public link is an unauthenticated LLM endpoint: the per-session rate limit exists but there is no per-widget daily cap.
- PROPOSAL: 1) Route apps/dashboard/src/app/w/[widgetId]/page.tsx (public, no auth, only mounts the loader with widgetId — never tenant slug). 2) Day-0 provisioning job: ensure one widget_configs row + one channel_accounts(type='web_widget') + agent binding per tenant (idempotent; reuse the bootstrap). 3) isWidgetOriginAllowed always allows the platform origin(s) from env. 4) New Redis counter widget:demo:{widgetId}:day with a plan-derived cap (TenantThrottleService) and a 'demo' flag on the session so analytics/activation exclude it. 5) Rate-limit the /w page itself by IP (existing CF-Connecting-IP throttle).
- evidence: apps/api/src/modules/widget/widget-public.controller.ts:62-140; apps/api/src/modules/widget/widget-security.ts:50-64; apps/api/src/modules/conversations/conversations.service.ts:5793

### E5 [major] Generated recipe for "Otro": no owner service, no persistence, and it must not run inside the alta request
- where: §3.2 second bullet, §4 Paso 1, §9 row "Receta generada", D9
- why: §9 sizes it as "prompt with fixed schema; router exists". The router exists (ai/router/llm-router.service.ts) but a fresh tenant has no plan tier context for llm-spend-guard.service.ts, completeOnboarding (onboarding/page.tsx:802) is synchronous, and there is no place to store a per-tenant recipe (the static registry is code). "Blank instead of invented" cannot be a prompt instruction alone.
- PROPOSAL: New modules/verticals/vertical-recipe-generator.service.ts + BullMQ job 'vertical-recipe' enqueued at step 1 (page polls GET /verticals/recipe/status; generic recipe shown as skeleton meanwhile). Prompt uses structured output whose JSON schema has NO price/address/phone fields at all; answers may contain the literal token [ ]; a deterministic post-validator rejects any digit+currency, street patterns or URLs not given by the owner and falls back to the generic recipe. Charge a platform-owned budget key in the spend guard (onboarding:<tenantId>, max 2 generations). Persist as tenants vertical config `recipe` (versioned JSON) and make getVerticalDefinition prefer it when industry='otro'.
- evidence: apps/api/src/modules/ai/router/llm-router.service.ts; apps/api/src/modules/ai/router/llm-spend-guard.service.ts; apps/dashboard/src/app/onboarding/page.tsx:802

### E6 [major] Step 5 "Escríbele": no event for "AI replied and it was delivered", and no way to tell owner's test from a real customer
- where: §4 Paso 5, §11 activation metric, §9 row Paso 5
- why: Only 'message.inbound' exists as a domain event (conversations.service.ts:2264). The AI reply reaches the dashboard as a WebSocket 'conversation:message' in a per-conversation room that requires joining with canViewConversation; the step-5 page does not know the conversationId in advance. 'Sent' only means accepted by the provider (memory: photos never delivered while status said Sent). Activation defined as "primer mensaje real respondido" needs a stage value; ONBOARDING_STAGES has none after channel_connected except completed.
- PROPOSAL: Emit 'message.ai_replied' {tenantId, conversationId, channelType, channelAccountId, messageId} next to the existing gateway.emitNewMessage at :2357, and on outbound status 'delivered' (WhatsApp/Messenger) emit 'message.delivered'. Gateway relays both to the tenant room as 'onboarding:first_contact'. Add GET /onboarding/first-contact (idempotent, DB-backed: first outbound with direction='outbound' AND sender='ai' per channel) so the page survives reloads. Add stage 'live' after channel_connected; advance it from the same handler; keep 'completed' for the summary screen.
- evidence: apps/api/src/modules/conversations/conversations.service.ts:2259-2270,2357; apps/api/src/modules/agent-console/agent-console.gateway.ts:603-609; packages/shared/src/onboarding-stage-contract.ts:26-32
